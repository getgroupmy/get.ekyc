Add identity verification to your app

GET eKYC checks identity documents (MyKad and the other Malaysian cards, passports, foreign ID cards), driving licences and vehicle documents, matches the selfie to the document photo, checks the person is live, and tells your server the result. This guide takes you from an API key to a working integration.

Your app takes photos→Your server calls GET eKYC→ create · upload · submit→webhook / poll→approved · review · rejected
One rule: call the API from your server, never from the mobile app or browser. The API key must stay secret: your app sends the photos to your server, and your server forwards them.

Hosted page: the recommended way

Like other eKYC providers, GET eKYC can run the whole capture itself. Your app does not build camera screens: it hands the user over to GET eKYC's page and gets them back when they are done. New checks, documents and capture improvements then reach your users without an app update.

Your server: create (with redirect_url)→Open hosted_url→ User: consent · document · selfie · head turns→Back to redirect_url→Webhook with the result
  1. Your server creates the verification (step 2 below) and adds "redirect_url": where to send the user afterwards. An https:// page or your app's own link, such as getride://ekyc-done. The answer has hosted_url, valid for minutes and for this one verification only.
  2. Send the user to hosted_url. On mobile, open it in the system browser view (iOS ASWebAuthenticationSession / SFSafariViewController, Android Custom Tabs; in Flutter flutter_web_auth_2 or url_launcher with LaunchMode.inAppBrowserView). These have camera access and return to your app link. In a plain WebView you must grant the camera permission yourself.
  3. The page does the rest: notice and consent (English / Bahasa Melayu), document photos with instant "we can't read this" feedback, the back of a MyKad when needed, selfie and the head-turn liveness. Vehicle documents skip the face steps by themselves.
  4. The user comes back to redirect_url?verification_id=ver_…&status=…&external_ref=…. status is approved, review, rejected, submitted (still checking), cancelled or expired. Use it only to choose the next screen.
  5. Trust only your server: the decision comes from the signed webhook (or GET /v1/verifications/{id} with your key). The return link can be typed by anyone, so never approve a user from it.
curl -s -X POST BASE/v1/verifications \
  -H "X-API-Key: $EKYC_KEY" -H "Content-Type: application/json" \
  -d '{ "external_ref": "driver-1042", "redirect_url": "getride://ekyc-done" }'
# → { "id": "ver_6f…", "hosted_url": "BASE/v/AbC…", "hosted_url_expires_at": "…", … }

Mobile apps (iOS and Android): three modes

All three use the same hosted_url from your server, and the result reaches your server by webhook in all three.

ModeThe user stays in your app?How
1 · SDK, native screensYesFlutter package get_ekyc: GetEkyc.start(context, hostedUrl: url). Native document camera, selfie and head turns captured automatically with on-device face tracking.
2 · SDK, hosted page in the appYesGetEkyc.start(context, hostedUrl: url, mode: EkycMode.webView). The hosted page runs inside the app; it can't navigate away, and reports back through the EkycBridge channel. Every server update reaches users at once.

1 · Get an API key

  1. Ask the GET eKYC owner for a console login with the Developer role (it sees only the keys you create).
  2. Sign in to the console (the owner gives you its address: it is not open to the internet) → API clients → enter your app's name and, optionally, a webhook URL → Create client. Or ask an admin to create the key for you.
  3. Copy the key (ek_…) and the webhook secret from the box. They are shown once; store them in your server's secret store.
  4. Send the key in the X-API-Key header on every call.

Lost the key? Revoke it and create a new one. Use Try it in the console to test photos before writing code.

2 · Create a verification

One verification = one person (or one vehicle document). Leave document_type out (or "auto") and GET eKYC detects it from the photo. external_ref is your user id: it links results to your user, lets you re-authenticate them later and keeps their own re-verifications from counting as duplicates.

curl -s -X POST BASE/v1/verifications \
  -H "X-API-Key: $EKYC_KEY" -H "Content-Type: application/json" \
  -d '{
    "external_ref": "driver-1042",
    "country": "MYS",
    "claimed": { "full_name": "Ali bin Abu", "document_number": "900514-10-5231" },
    "consent": { "version": "2026-11", "accepted_at": "2026-11-24T09:30:00Z" }
  }'
// Node 18+ / Deno / Supabase Edge Function

3 · Upload the photos

Using the hosted page? Skip steps 3 and 4: the page uploads and submits for you.

One PUT per image, as multipart form field file (JPEG, PNG or WebP, up to MB). Kinds: document_front, document_back (optional; recommended for MyKad), selfie, liveness_1…liveness_3. Each answer includes image quality, so your app can ask for a retake right away.

curl -s -X PUT BASE/v1/verifications/$ID/media/document_front \
  -H "X-API-Key: $EKYC_KEY" -F file=@front.jpg
async function upload(id, kind, bytes /* Uint8Array */) {
  const form = new FormData();
  form.append("file", new Blob([bytes], { type: "image/jpeg" }), `${kind}.jpg`);
  const r = await fetch(`${BASE}/v1/verifications/${id}/media/${kind}`, {
    method: "PUT", headers: { "X-API-Key": key }, body: form,
  });
  return r.json();   // { kind, quality: { sharpness, brightness, glare, ... } }
}
for (const kind of v.required_media) await upload(v.id, kind, photos[kind]);

Photo tips for your capture screen: fill the frame with the card, no flash glare, rear camera for documents, front camera for the selfie, face the camera in even light.

4 · Submit

curl -s -X POST BASE/v1/verifications/$ID/submit -H "X-API-Key: $EKYC_KEY"

Returns 202 with status: "processing". A check takes a few seconds. Missing photos return 422 with the list. Unsubmitted sessions expire after minutes.

5 · Get the result

Use the webhook (recommended) or poll every 1–2 seconds:

curl -s BASE/v1/verifications/$ID -H "X-API-Key: $EKYC_KEY"
statusMeaningWhat your app does
processingStill checkingWait
approvedAll checks passed (or a reviewer approved)Let the user continue
reviewA person will decideShow "We're checking your documents"; wait for the webhook
rejectedA check failedShow reason_details[].message; offer a retake when the reason is about photo quality

Every answer carries reasons (codes) and reason_details (code + a message you can show the user).

Webhooks

If your client has a webhook URL, GET eKYC POSTs the result there when a case is decided, automatically or by a reviewer (3 attempts). Answer with any 2xx.

{ "event": "verification.completed", "id": "ver_6f…", "external_ref": "driver-1042", "test": false,
  "status": "approved", "reasons": [], "decided_by": "auto", "completed_at": "2026-11-24T09:31:12Z" }

Always verify the signature before trusting it: X-EKYC-Signature must equal "sha256=" + HMAC_SHA256(webhook_secret, X-EKYC-Timestamp + "." + raw_body), and the timestamp should be recent.

import crypto from "node:crypto";

export function verifyEkycWebhook(secret, timestamp, rawBody, signature) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`).digest("hex");
  const fresh = Math.abs(Date.now() / 1000 - Number(timestamp)) < 300;
  return fresh && crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
}
import hashlib, hmac, time

def verify_ekyc_webhook(secret: str, timestamp: str, raw_body: bytes, signature: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), timestamp.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature) and abs(time.time() - int(timestamp)) < 300
// Supabase Edge Function / Deno
async function verifyEkycWebhook(secret: string, ts: string, raw: string, sig: string) {
  const k = await crypto.subtle.importKey("raw", new TextEncoder().encode(secret), { name: "HMAC", hash: "SHA-256" }, false, ["sign"]);
  const mac = new Uint8Array(await crypto.subtle.sign("HMAC", k, new TextEncoder().encode(`${ts}.${raw}`)));
  const expected = "sha256=" + [...mac].map(b => b.toString(16).padStart(2, "0")).join("");
  return expected === sig && Math.abs(Date.now() / 1000 - Number(ts)) < 300;
}

Document types

Sent as document_type, or detected when you leave it out. Identity documents need a selfie; vehicle documents don't.

document_typeDocumentCategorySelfie

Not sure what the user uploaded? Detect it first.

Liveness capture

liveness_challenge is a random order of center, left and right. In your app:

  1. Show the steps one at a time: "Look straight at the camera", "Turn your head to the left", "Turn your head to the right" — in the order given.
  2. Take one frame per step with the front camera, in order, and upload them as liveness_1, liveness_2, liveness_3.
  3. Take the frames live, in your app: never let the user pick them from the gallery.

Turns must be clear and in opposite directions (mirrored front cameras are fine). Every frame must be the same person as the selfie.

What comes back

result.extracted holds what was read from the document; result.checks lists every check with status (pass / review / fail / skipped) and details; result.scores holds face_match (0–1) and face_score (0–100, 80 = match threshold); result.engine_version is the GET eKYC version that decided it.

Other calls

Detect a document (nothing stored)

curl -s -X POST BASE/v1/verifications/detect -H "X-API-Key: $EKYC_KEY" -F file=@photo.jpg
# → { "document_type": "national_id", "subtype": "MyKad", "country": "MYS", "needs_selfie": true, "needs_back": true, ... }

Re-authenticate a verified user (e.g. a driver going online)

Matches a new selfie against the face from that user's latest approved verification. Nothing is stored.

curl -s -X POST BASE/v1/verifications/reauth -H "X-API-Key: $EKYC_KEY" \
  -F external_ref=driver-1042 -F selfie=@now.jpg
# → { "match": true, "similarity": 0.71, "threshold": THRESH, "verification_id": "ver_6f…" }

Compare two faces

curl -s -X POST BASE/compare -H "x-api-key: $EKYC_KEY" -H "Content-Type: application/json" \
  -d '{"image1": "<base64>", "image2": "<base64>"}'
# → { "similarity": 0.87, "verified": true, "cosine": 0.6, "model": "SFace" }   (422 {"error":"no_face"})

List and delete

curl -s "BASE/v1/verifications?external_ref=driver-1042&status=approved" -H "X-API-Key: $EKYC_KEY"
curl -s -X DELETE BASE/v1/verifications/$ID -H "X-API-Key: $EKYC_KEY"   # erases images and personal data

Download a photo of your own verification (for example to keep the ID image with your user):

curl -s BASE/v1/verifications/$ID/media/document_front -H "X-API-Key: $EKYC_KEY" -o front.jpg

Rules & limits

  • Keys: server-side only; one key per app; revoke a key that leaks and create a new one.
  • Images: up to MB each; at least 480 px on the short side; documents flat and sharp.
  • Sessions: submit within minutes of creating.
  • Tests: send "test": true while integrating; test runs are deleted after hours.
  • Consent: record the user's consent (consent) before taking photos — biometrics are sensitive data under the PDPA.
  • Privacy: images and personal data are stored encrypted; delete a user's data with DELETE when they ask.
  • Decisions: a review is decided by a person; plan your app for a wait.
  • Stability: /v1 only grows: new fields, document types and reason codes are added, nothing is renamed or removed. Ignore fields you do not know and act on status. A breaking change would come as /v2, with /v1 kept running.
